- 研究编号：`feasibility-20260823-01`
- 使用模型：`deepseek / DeepSeek-V4-pro`
- 执行规模：3 名执行角色、1 名独立 Spec 确认角色、3 个任务、9 个产品 session
- 流程执行状态：`COMPLETE_PROTOCOL_VALID_MECHANICS`
- 真人审阅有效性：`NOT_EVALUABLE_REVIEW_NOT_PERFORMED`
- 模式工程价值：`SUPPORTED_BY_PILOT_EVIDENCE`
- 量化提效结论：`NOT_EVALUABLE_PILOT_ONLY`
- 综合表述：**工程价值成立，量化收益未证明**

## 一、测后重要更正

试跑结束后，协调者明确说明：所有最终 `ACCEPT` 都是在没有查看具体代码改动的情况下提交的。

这意味着原始 CSV 中的计时、workspace、配对 digest、人工决定冻结时间以及隐藏 Oracle 顺序仍然是真实记录，但下面两个指标不能按原计划解释：

1. **真人决定准确率不可评价。** `ACCEPT` 不是基于代码或 Diff 的实质审阅决定，因此不能把 false acceptance 归因于 A、B 或 C 模式。
2. **完整真人总人时不可评价。** 当前时间只覆盖需求阅读、HITL 操作和结果页面停留等活动，没有包含完成可信代码审阅所需的真实投入，只能视为操作时间下限。

因此，本报告保留所有原始观察，但不再把 9 个 session 的 `ACCEPT`、false acceptance 或采集到的人时用于判断 ChangeSpec 是否提效。这不等于模式没有价值；模式的工程价值与量化效率价值必须分开判断。

## 三、哪些结论仍然有效

以下是机器证据或流程证据，不受“没有审阅代码”这一问题影响：

- 9 个 session 均完成了独立 workspace、任务分配、计时和结果冻结流程。
- 3 组 B/C 使用了完全相同的锁定 Spec digest。
- 每名执行参与者没有重复接触同一个 fixture。
- Scope 为 9/9：最终业务改动均限制在任务允许文件内。
- 隐藏 Oracle 全部在人工决定冻结之后运行。
- 客观正确率的原始观察为 A 1/3、B 1/3、C 2/3。
- C 三场的公开 Verifier 首轮均通过，因此 Evidence 修复机会为 0/3，修复次数也为 0。
- A/B/C 路径、HITL、锁定 Spec、Verifier、候选冻结和 Oracle 封存可以端到端运行。

客观正确率每个“任务 × 模式”只有一次观察，只能描述本次模型产物，不能据此断言某种模式更好或更差。

## 六、这是否说明模式有问题

**不能这样下结论。**

本次试跑说明模式的机械流程可以工作：

- B/C 配对 Spec 能被独立确认、锁定并复用；
- B 能关闭 Evidence 修复；
- C 能在公开 Verifier 失败时具备一次修复能力；
- HITL、公开 Verifier、Scope 与结果持久化均能运行；
- 所有 session 的改动范围都符合任务要求。

本次真正暴露的是**真人评测流程与产品审阅入口不够强**：测试数量多、操作时间长时，参与者可以在没有查看具体 Diff 的情况下直接接受结果。这个问题会让“可信产品决定”和“真人总人时”失真，但不能据此判断 ChangeSpec 模式本身无效。

同时仍需注意一个独立的机器证据：部分候选通过了公开验证，却没有通过隐藏 Oracle。C 因公开验证已经 PASS 而没有修复机会。这说明公开证据覆盖仍有改进空间，但它与参与者是否认真审阅是两个不同问题。

## 七、建议的修正版试跑流程

正式研究前，建议先做一次规模很小的纠正试跑，不直接启动 117-session 研究：

1. 在最终决定前强制展示 `changed_files` 和完整 Diff。
2. 要求参与者逐项检查“需求—代码—测试证据”，并勾选简短审阅清单。
3. 没有打开 Diff 或停留时间明显不足时，不允许提交 `ACCEPT`。
4. 明确区分公开测试通过、代码审阅通过和最终接受，不能把三者合成一个按钮。
5. 计时器增加独立的 `code_review` 类别，结果审阅不能只记录查看摘要的时间。
6. 每个真人只扮演自己的角色；协调者不能代替其他参与者提交最终决定。
7. A 路径也要增加与 B/C 可比的产品阶段耗时遥测。
8. 在查看正式结果前预注册人时非劣界值。

## 八、业务价值情景估算

下面是基于实测确认耗时的盈亏平衡估算，不是已经实现的财务收益：

- 三个任务的独立 Spec 确认时间分别为 185.36、148.54、121.90 秒，平均为 **151.93 秒，即 2.53 分钟/任务**。
- 假设工程师综合成本为 200 元/小时，则确认成本约为 **8.44 元/任务**。
- 假设一次需求偏差、越界修改或错误返工平均消耗 2 个工程师小时，即约 400 元。
- 盈亏平衡点为 `8.44 ÷ 400 ≈ 2.11%`：只要每 100 次变更减少约 2.1 次此类返工，就能覆盖 Spec 确认投入。
- 若一次事故或返工平均消耗 4 小时，盈亏平衡点下降到约 **1.05%**。
- 以每月 100 次变更、减少 3 次两小时返工为示例，理论毛节省约 1,200 元，减去约 844 元确认成本后，净收益约 356 元/月；该示例未计 Token、基础设施和管理成本。

这套估算的意义不是证明当前已经节省了多少钱，而是给产品负责人一个可验证的商业门槛：后续正式实验只需判断 ChangeSpec 是否能将高成本返工率降低到盈亏平衡线以上。

## 九、最终结论

- **流程可行性：通过。**
- **模式工程价值：成立。** 契约锁定、范围治理、验证闭环和可审计性均有直接运行证据。
- **模式是否有问题：本次数据不支持“模式有问题”的结论。**
- **模式是否提效：不可评价。**
- **模式是否提高正确率：不可定论，仅保留小样描述。**
- **真人决定准确率：不可评价。**
- **完整真人总人时：不可评价，只采集到了操作时间下限。**
- **客观模型产物质量：保留 A 1/3、B 1/3、C 2/3 的小样原始观察，但不能外推。**
- **下一步：先修正真人审阅流程，再决定是否进行新的小规模可行性复跑。**
